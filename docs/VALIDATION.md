## 真实 Mihomo 联调

使用官方 GitHub 发布 `Mihomo Meta v1.19.33 darwin arm64 / go1.20.14`。
官方压缩资源 SHA-256：

```text
e3f999eea69c921bf6c7fbd265973e7c01aef0cc17962b00feb52b1a53a79109
```

解压后文件 SHA-256：

```text
6e214ab9ed9815a017f6fd8dd34ded928e9028c78b6d0ef2f96f4d41a18b5051
```

文件仅放入独立临时测试目录，不进入 App 包或源码。
App 内整包下载在当前网络下超时；随后从同一官方地址分段下载并核对官方摘要，
用于验证用户手动放置内核的路径。因此本次不将 App 内完整下载标记为成功。

联调配置显式关闭 TUN、DNS 监听及 mixed/http/socks/redir/tproxy 端口，
没有设置系统代理、修改系统 DNS 或路由，也没有安装 root 服务。

验证结果：所选内核 `-t` 通过；helper 启动、Unix API 就绪；
仅保存原文时运行模式维持 `rule`；应用后运行模式变为 `global`，PID 不变，
`mixed-port=0`、`tun.enable=false`；连接、策略组及日志可以读取；最终已停止测试内核。

## 校验长时间显示“正在处理”的修复

实际诊断：用户配置引用了尚未下载的地理规则数据库。Mihomo 的 `-t` 校验
先下载 MMDB，再尝试下载 GeoSite.dat；09:39:44 返回 GeoSite 下载超时，
没有已应用版本，也没有启动内核。原界面会继续保留操作开始时的画面。

修正后，主窗口显式使用后台不节流的原生刷新路径。构建时给固定的 MyGo
v0.7.4 生成局部兼容副本，原生表面在该选项开启时不依赖显示刷新或遮挡状态；
依赖缓存不修改。启动时也避免重复创建主窗口。

校验输出现在逐行进入日志和阶段状态，界面轮询不因忙碌而停止；显示最近输出、
耗时和取消按钮。校验有 90 秒上限，取消或超时会结束校验进程；失败错误取关键
错误行，完整输出在日志页。App 重连也会显示 helper 已报告的错误。

新增回归覆盖：退出前即可读取下载进度；取消和超时清除操作阶段且不提交版本；
下载错误不再显示为“仍在下载”。实际原生窗口验证：无额外点击时自动显示下载
失败并恢复按钮；后台配置变化自动刷新；长校验显示下载阶段及已用秒数；取消后
自动恢复操作。验证使用独立受控内核，没有改动用户配置或系统网络。

未获 SHA-256 授权的内核在进入校验前被拒绝；动态自签名检查通过；
完整 race detector 测试与 go vet 通过。

首次真实管理员安装发现 umask 077 将公开注册记录缩减为 0600，导致 GUI 无法读取。

修复安装时优先保留已有系统配置，不以旧的普通用户副本覆盖。
真实系统授权后验证通过：

- launchd 的 `dev.nativejet.helper` 状态为 running；GUI 显示“已安装系统后台服务”“已连接 · 可以启动 TUN”。
- helper、注册记录和 plist 均由 root 所有，权限分别为 0755、0644、0644。
- 已安装 helper、App 内 helper 与注册记录的 SHA-256 一致；绑定当前用户 UID 501，授权 1 个内核。
- 非 GUI 的系统 curl 连接被拒绝，返回空响应，不暴露配置。
- GUI 保留 1 份配置和所选 Mihomo v1.19.33；原开发 state.json 与安装前备份逐字节一致。
- 内核保持停止；未启动 TUN，未改变当前路由或 DNS。

真实 TUN 转发、服务随系统重启恢复及休眠唤醒仍待单独系统回归。


## 具体启动错误与内核日志（0.2.2）

启动与配置热加载按每次操作的日志游标提取内核错误，避免旧错误或 helper 摘要掩盖根因。
TUN 路由已存在时明确显示冲突网段、关闭其他 TUN 后重试的说明以及内核原文；
监听地址或端口占用也给出明确提示。没有具体内核错误时保留核对失败的实际值，不猜测原因。

标准输出/错误输出的接收改为等待 os/exec 完成复制后再汇总，保留退出前没有换行的最后一行。
日志页显示实时 API 日志和启动输出，增加来源筛选、完整原文查看与复制；
即使停留在其他页面也拉取日志，失败后“查看内核日志”定位最近的内核错误。
错误提示支持换行显示。

已通过完整 race detector 测试与 go vet，包括模拟 TUN 路由冲突、热加载失败回退、
无换行 fatal 输出、历史错误隔离、重试成功、内核日志流和重叠拉取去重。
在独立普通用户数据目录中用不会创建 TUN/网络监听的模拟内核验证原生窗口：
启动后直接显示“TUN 路由冲突：路由 1.0.0.0/8 已存在”，查看日志自动选中真实启动错误；
来源筛选为“启动输出”后仅显示对应输出，完整内容保留原始行。
日常用户的配置和系统网络未用于该模拟测试。

## 后台服务更新稳定性（0.2.3）

加入延迟卸载、临时 bootstrap 失败及持续失败的回归。

本次未启动真实 TUN；错误呈现和日志行为由上述独立模拟及集成测试验证。

## Windows x64（2026-11-08）

在 Windows 10 企业版 Build 19045 的 x64 测试机上经 SSH 验证，内核为官方 Mihomo v1.19.33。

- 普通权限的交互桌面创建了原生窗口，能访问已安装的服务，也能启动并连接普通用户 helper。未授权的 LocalService 使用同一访问掩码打开系统服务管道时收到拒绝。
- SCM 服务安装、升级、内核 SHA-256 授权和卸载通过。升级保留了授权与已应用版本，卸载前后状态文件摘要一致。
- 真实内核通过本地命名管道提供连接和 GeoData 信息。应用一份 Mihomo 拒绝的配置后，helper 用上一版本重新启动内核。
- 只接管两个保留测试地址时，TUN 分别传输了 TCP/HTTP 和 UDP/DNS 数据。正常停机和强制终止 helper 都移除了测试路由，原有默认路由和 DNS 保持原值。重新启动服务后能读取持久化状态。
- Windows 的 IPC、安装清单篡改和 ZIP 资源筛选专项测试通过。Windows x64 与 ARM64 ZIP 均通过构建和归档校验。

Windows 11 和 ARM64 的运行验证，以及交互式 UAC 授权和整机默认路由场景，需要相应测试环境。
